# NetIQ Identity Package Deployment Tool 1.0 — analysis and what DirXMLDev should adopt

Analyst report, 2026-09-09. Inputs: the unzipped PDT 1.0.0 distribution in `~/Downloads/IDM_PackageDeploymentTool_1.0.0/` (config, scripts, logs of the Aug 2023 run, and the fat jar `pdt-rest-1.0.0.0000.jar` decompiled with CFR), the Designer 4.10.1 install at `/Applications/Designer` (the `com.novell.idm.rcp` plugin that PDT drives, decompiled), the product docs (release notes, the user-guide PDF), and the DirXMLDev repo docs and deploy/edit sources. Everything below is labelled **[code]** (read in decompiled source), **[log]** (seen in the run logs), **[docs]** (the vendor documentation), or **[inferred]**.

Two findings frame everything else:

1. **PDT does not contain any package logic of its own.** It is a Dropwizard REST server plus an Angular UI that writes JSON files to disk and then shells out to `Designer -application com.novell.idm.rcp.DesignerHeadless -command …`. Every install, upgrade, downgrade, uninstall, deploy and import is performed by Designer's headless application, which runs a full Eclipse/OSGi workspace, creates a throw-away Designer project, imports the driver set from the vault, manipulates packages with Designer's `PackageUtil`, and calls Designer's own whole-vault deploy. **[code]**
2. **The headless application PDT depends on ships inside every Designer ≥ 4.8.7, including the 4.10.1 on this Mac** (`/Applications/Designer/plugins/com.novell.idm.rcp_4.0.0.202507091432/com/novell/idm/rcp/DesignerHeadless.class`, registered in that plugin's `plugin.xml` as `org.eclipse.core.runtime.applications` id `DesignerHeadless`). **[code]** So the thing worth adopting is not PDT; it is the headless Designer command surface PDT was built on — usable from DirXMLDev with a `ProcessBuilder` and no REST server in between.

Also worth stating up front: the logs in the distribution show that PDT was started three times (2023-08-15, 2023-08-17) and never got past login. Every `POST /api/pdt/v1/user/login` returned 500 with `IllegalArgumentException` at `com.netiq.ism.obfuscate.CryptoUtils.decipher(CryptoUtils.java:400)` ← `PDTAuthenticator.authenticate` ← `SessionService.login`, because `pdtPassword:` in `config.yml` is empty (the `create-password-config` script, which enciphers the password with the keystore and writes it into `config.yml`, was never completed). No package or deploy operation ever ran on this machine, so runtime behaviour below comes from the code, not from observed runs. **[log]**

### 1.2 The Designer headless command surface PDT drives **[code — both sides]**

PDT builds, per operation, a command of the form (`PDTConstants`):

```
<designerBasePath>/Designer[.exe] -nosplash -application com.novell.idm.rcp.DesignerHeadless -nl en
   -command <deployDriver|redeployDriver|deployDriverSet|redeployDriverset|redeployIDV|upgradePackage|importIDV>
   -p <designerPackagePath> [-v] -u <projectName> [-d] [-r] [-m] [-I|-q] [-V]
   -a <adminDN> -w <password> -s <host:port> -c <driverSetDN> [-j <serverDN>]
   -b <packageSpec> -D "<driverNames>" -F "<propsFile>[&<propsFile>…]" [-P &] -l <logFile>
   [-z "<…>"] [-y "<…>"] [-k "<…>"]
```

On the Designer side, `DesignerHeadless.start()` parses with `com.novell.idm.rcp.prompts.InteractiveInfoProvider.getOpt` (option string `"?hgmtexSdvrqVIu:L:O:i:p:w:n:l:f:o:a:s:c:b:D:F:P:k:y:z:j:"`) and dispatches on `-command` to one `BasicHeadlessCommand` subclass. The full command list in Designer 4.10.1 is: `deployDriver` → `DriverDeployCommand`, `deployIdvPackage` → `DeployIDVPackage`, `validatePackage` → `ValidatePackageCommand`, `docGen` → `DocGenCommand`, `listContents` → `GetDriverListCommand`, `importIDV` → `ImportIDVCommand`, `createUAPackage` → `CreateUAPackage`, `upgradePackage` → `UpgradePackage`, `deployDriverset` → `DriversetDeployCommand`, `redeployDriver` → `DriverRedeployPackage`, `redeployDriverset` → `DriversetRedeployCommand`, `redeployIDV` → `IDVRedeployCommand`. PDT uses seven of these; `validatePackage`, `docGen`, `listContents` (`-L L` lists drivers, `-L P` lists packages) and `createUAPackage` (uses `packagemanager.actions.BuildPackageAction` / `NewPackageVersionAction` / `PublishPackageAction`) are available and unused.

Option semantics (from `InteractiveInfoProvider` field names and the commands that read them):

| Option | Meaning |
|---|---|
| `-p dir[:dir…]` | package directories; each jar in them is **installed as an OSGi bundle** (`BundleContext.installBundle("file://…")` + `start()`) by `PackageOperation.addPackages`, then `PackageUtil.getPackageBundles()` enumerates them. Files containing `.feature_` or `.properties` are skipped. |
| `-u name` | project name in the headless workspace (`-data`). PDT passes `<stageSetId>_<stageId>_<timestamp>` for deploys and `projectName: IDM_PDT` for upgrades. |
| `-d` | `shouldOverwrite`: delete and recreate that project first. |
| `-OL` | `shouldOverwriteDuringDeploy` → passed as `doNotOverwrite` to `IdentityVault.deploy(...)` and as `turnOffLogging` (driver-set log limit 0). |
| `-v` | `versionSupport`: every name in `-b` carries `_<version>`; **also suppresses the automatic `startDrivers` after deploy** (`if (!this.m_versionSupport) startDrivers(...)`). PDT always passes `-v` when the recipe has a base version, so PDT deploys leave drivers stopped. |
| `-m` | `mandatoryOnly` → `PackageUtil.getDependencyBundles(list, catalog, results, populateOnlyMandatory=true)`: optional feature sub-packages are not auto-added. PDT passes `-m` on every upgrade/downgrade/uninstall and on driver-set/IDV installs; not on `deployDriver`. |
| `-r` | `requiredPackages`: in `-b`, each driver's entry is `BASE_ver:DEP_ver;BASE_ver:DEP2_ver` and drivers are separated by `,` (parsed by `UpgradePackage.getDependentMap`). |
| `-I` / `-q` | install-only / uninstall-only mode (`m_isInstallDriver` / `m_isUninstallDriver`), used by `InstallService` and `UninstallService` with `-command upgradePackage`. |
| `-b spec` | package spec. Grammar as PDT emits it: entries separated by `;`, each `BASE[_ver]:PKG[_ver]`; on redeploy an `::` separates the install list from the **uninstall list** (`DriverRedeployPackage` splits on `"::"` and calls `parseDriversToUnInstallVersion` on the second half). When only a base package is wanted, `-b BASE_ver`. |
| `-D names` | driver names, `:`-separated; **base64-encoded on Linux** (`Core.isLinux()`), plain on Windows — PDT mirrors this. |
| `-F files` `-P sep` | one prompt-answers properties file per driver, separated by `-P`'s value (PDT uses `&`; Designer's default separator is `\|`). |
| `-a -w -s -c -j` | admin DN, password (**`-w env:VARNAME` reads the password from the environment** — Designer supports it, PDT does not use it and passes the password in clear on the command line, masking it only in its own log), `host[:port]`, driver-set DN, preferred server CN for multi-server driver sets. |
| `-f path` | (`deployDriver` only) **export to a file instead of deploying**: `installPackagesOnDrivers` then `DeployExporter.exportIdentityVault` with `DeployProjectAction.setFileExport(true)`. No vault connection is made on this path. |
| `-g` | `generatePrompts`: writes `<driverName>.properties` with every prompt of the resolved packages (`PackageOperation.generatePackagePromptsOnDrivers`), no deploy. |
| `-z -y -k -V` | PDT-specific import plumbing: driver CN list (`;`-separated), stage hierarchy folder, PDT home directory, driver-set-only import. |
| `-l dir` `-t` `-x` `-S` `-e` | log directory (`HeadlessLogger`), trace, exit immediately, secure LDAP, don't set security equivalences. |

What one `upgradePackage` run does, in order (`UpgradePackage.execute`) **[code]**: open/create the Eclipse `Workspace`; `getIDMProject` (create or reuse the named project via `ProjectManager.addProjectv2` / `initProjectV2`); `getIdentityVaultandDriverSet` (model objects with host/admin/password/context); `LiveOperation(vault, …)` and `PackageOperation(vault, catalog, dSet, packageDir)`; `addPackages` (OSGi-install every jar) and `populatePackageBundle`; parse `-b` into `m_packagetoVersionMap`; `setupDSAccess` (`com.novell.core.datatools.access.nds.DSAccess.buildDSAccess`, Designer's admin-namespace client, with one retry); **`importFromEdirectory`** — a `DeployImportAction` over targets `[driver set, "[Schema]", cn=Default Notification Collection]` filtered to the named drivers; for each imported driver find its base package (`PackageUtil.getBasePackage(driver)`, else "This driver upgrade will be skipped"); `populatePackages` → `PackageUtil.getDependencyBundles` + `PackageUtil.doImport` into the catalog; `saveProject`; **`installPackagesOnDrivers`**; `saveProject`; `setupDefaultServerOE`; **`deployIDVaultContents`** = `IdentityVault.deploy(true, true, true, doNotOverwrite, results)` (Designer's whole-vault deploy of the project, then `EventManager.deployEvent` for plugin contributions such as provisioning `ds-object`s); `updateSecurityEquivalences` (adds the admin as security-equal if the driver has none); `startDrivers` unless `-v`; exit code 0 or -1, and the log ends with `#OPERATION_SUCCESS` or `#OPERATION_FAILED`. `DriverDeployCommand` and `DriverRedeployPackage` delete the project afterwards (`deleteProject`); `UpgradePackage` does not.

`installPackagesOnDrivers` **[code]** is the merge policy: for each `(shortName, version)` in the driver's resolved package map, target = vault (type 4), driver set (type 3) or the driver(s) of that name (type 2); `checkPackageOperation` compares with the target's `getInstalledPackages()` and yields a `PendingOperation` code — 0 same version, 1 install, 2 uninstall, 3 upgrade, 4 downgrade; prompt answers are patched with `PackageUtil.patchAllGCVValues(pkg, props, prompt, target)`; then **upgrade and downgrade are both implemented as `PackageUtil.uninstallPackage(target, old)` followed by `PackageUtil.installPackage(target, new)`**, with `pkg-version-change` transient data set on both package objects so the package layer can treat it as a version change rather than a removal; "same version" is skipped (`continueOnPackageInstall()` always returns true). Whether Designer preserves customized items across that uninstall/install is decided inside `PackageUtil` (`removeCustomizations`, `checkPendingUpgrade` are private there) — I did not decompile `idm.jar`'s `PackageUtil` body, so **customization handling on upgrade is unverified; treat it as "whatever Designer does in the Package Upgrade wizard, without the wizard's prompts"** **[inferred]**. The packagemanager plugin has the pieces (`commands.CompareCustomizations`, `RevertCustomizations`, `SyncCustomizations`, `RepairPackage`, `actions.RevertItemToPackageAction`, `SyncItemToPackageAction`, `PackageUpgradeInfoAction`), none of which the headless commands call.

### 1.3 PDT's own request flow **[code]**

Every service method: load `environments.json`, validate the stageSet/stage/idv/driverSet/driver ids, read the driver's recipe JSON, convert it to a properties file (`JsonToProperties.convertJsonToProperties`, written to `<designerBasePath>/<Driver>_<MMddyyyy_hhmmssSSS>.properties` with `deleteOnExit`), build the command, `exec`, and answer `"… request initiated successfully, refer <log> for details"`. Deploys run in a 5-thread executor (`DriverDeploy implements Callable<DeployStatus>`), wait for the exit code, write `deployStatus` (`"Last Deployment Completed :<epoch>"` / `"Last Deployment Failure :<epoch>"`), set `deployed=true`, clear `uninstallPacakgeList`, and delete the properties file; **install / uninstall / upgrade / downgrade are fire-and-forget** (`run.exec(cmd)` with no `waitFor`), so their only status is the Designer log file the UI polls. There is a hard limit of 5 drivers per deploy request (`"Number of drivers greater than 5"`).

## 3. Package lifecycle deep-dive

### 3.1 What a package jar contains **[code + local catalog]**

Designer's catalog is `<Designer>/packages/eclipse/plugins/<SHORTNAME>_<version>.jar` (e.g. `MFAZURCOENTL_1.1.0.20190802104848.jar`), with a `features/` sibling folder of Eclipse feature jars that the update site's `site.xml` indexes (`PackageDownloadService.readSiteXMLData` reads `<feature url= version=>` elements; `readNUpdateFeatureJar` reads `label` and `provider-name` from `feature.xml`). Each package jar is an OSGi bundle (`META-INF/MANIFEST.MF` with `Bundle-SymbolicName`, `Short-Name`, `Type`, `Base-Package`, `Internal-Version`, base64 `Supported-Drivers` / `Dependencies` / `Features`), a `plugin.xml` `packageregistration` extension, and `package_import.xml` — the document PDT parses (`<package id= name= version= base-package= type= symbolic-name= category= category-folder=>`, `idm-*` metadata, `idm-installationdirective/installation-directive/{features/{mandatory,optional}, dependencies, supported-drivers, ds-attributes}`, and a `package-folder` tree of `ds-object`s with per-object directives). Package `type`: **2 = driver, 3 = driver set, 4 = Identity Vault** (`PackageOperation.installPackage`, `EnvironmentRecipeBindingService` `commonSettings.type`). This matches what plan.md Phase 7 already recorded from the same catalog.

### 3.2 Route A — drive Designer headless from DirXMLDev (what PDT does, minus PDT)

Feasibility: **high; the runtime is on this machine.** `DesignerHeadless` and all twelve command classes exist in `/Applications/Designer/plugins/com.novell.idm.rcp_4.0.0.202507091432`; the community history says the application has existed since Designer 4.0 and 4.8.7 added "version selection" (`-v`), the PDT import hooks (`-k -y -z -V`) and the install/uninstall modes (`-I -q`). It cannot be run from a plain JVM: `BasicHeadlessCommand.init` constructs `org.eclipse.core.internal.resources.Workspace`, `PlatformURLResourceConnection.startup`, and the commands use `org.eclipse.ui.actions.WorkspaceModifyOperation`, `IDMPlugin.getInstance().getPreferenceStore()`, `DesignerActivator.getBundleContext()` (to OSGi-install the package jars) and Designer's `DSAccess`. It must be launched as the Designer executable with `-application com.novell.idm.rcp.DesignerHeadless -data <workspace>`; that is exactly what PDT does with `Runtime.exec`.

Three usable modes, in increasing coupling:

1. **Offline export producer (no vault touched).** `deployDriver -f <out.xml> -p <plugins> -u <proj> -d -b BASE[_ver]:FEATURE[_ver];… [-m] -F <answers.properties> -l <logdir>`: `DriverDeployCommand.execute` takes the `m_configPath` branch — `installPackagesOnDrivers` into a new project, then `DeployExporter.exportIdentityVault` to the file; `setupDSAccess` is never called on that branch **[code]**. `-g` with the same `-b` writes `<driver>.properties` listing every prompt (`# Prompts for Package = SHORT` / `GCV Name : n; GCV Type : t; GCV Prompt : p = `) so an agent knows what to answer. DirXMLDev then does `driver.add --from-export out.xml` and everything downstream (validate, simulate, diff, deploy with snapshot). This gives **install of a new packaged driver** with zero new deploy code and no secrets on a command line (no `-w`).
2. **Upgrade/downgrade/uninstall on an existing driver, vault-mediated.** `upgradePackage -v -u <proj> -d -r [-m] [-q|-I] -a -w env:IDM_PW -s host:port -c <dsDN> -b … -D <names> -F … -l …` — imports the driver from the vault, changes packages, and deploys back through Designer. This bypasses our plan/snapshot/verify, so if used it should be wrapped: `vault.diff` before (must be empty: tree == vault), snapshot, run headless, `import-live` afterwards into a commit, `vault.diff` against the pre-state to show exactly what the upgrade changed, and refuse on a `prd` tier. Acceptable as an interim on dev/stg, not as the long-term mechanism.
3. **Upgrade in a project without a vault** — untested: `UpgradePackage.execute` calls `setupDSAccess()`; if it returns null it logs an error and skips the import but still runs `populatePackages`/`installPackagesOnDrivers` on drivers found by name in the (pre-existing, `-u` without `-d`) project, then skips the deploy. Combined with the Phase 6 project writer this could become "upgrade in the project, export, import into the tree". Needs a spike; the `-f` export exists only on `deployDriver`, so the second half would be a normal Designer export of the project by other means.

Risks and costs of Route A: Designer must be installed where DirXMLDev runs (Windows/Linux per the PDT release notes; the Mac build is present here but headless launch on macOS is unproven — first spike); a run takes an Eclipse start-up, a project create, and (mode 2) a full driver-set import (minutes, not seconds); output is an exit code, a log with `#OPERATION_SUCCESS`/`#OPERATION_FAILED`, and Designer's `StatusResult` lines; the prompt-file format is undocumented but simple (parsed by `DriverPromptsResponse`: lines `# Prompts for Package = <short>` open a package section; `GCV Name : <n>; GCV Type : <t>; GCV Prompt : <p> = <value>` lines answer prompts; empty values are skipped, PDT writes `eNull` for them); Linux requires base64 for `-D`/`-z`/`-y`/`-k`; and the `-m` behaviour (mandatory-only dependency resolution) is the likely cause of the documented known issue that mandatory features' sub-packages under "Connected System" are not selected for SOAP/JMS **[inferred]** — our command builder should resolve features from the catalog reader and list them explicitly in `-b` rather than rely on `-m`.

### 3.3 Route B — native package install in the tree (plan.md Phase 7)

What Designer's package layer does that we would reimplement: dependency resolution over `Dependencies`/`Features` with mandatory vs optional and the "pyramid" rule (driver pkg → driver-set pkg → IDV pkg; docs p. 32); creating the `ds-object`s from `package_import.xml` at the placement the per-object directive names, with linkage weights (`<policy-linkage><policy-set channel= name= order="Weight" value="500"/>`); substituting prompt answers into `global-config-values` and other prompt-driven resources (`PackageUtil.patchAllGCVValues`); stamping package identity on each object (`idm-packageguid` → `DirXML-pkgGUID`, `idm-packageassocguid` → `DirXML-pkgAssociationId`, content/directive checksums → `DirXML-pkgChecksum`, initial state → `DirXML-pkgInitialState`) and the installed-package record on the driver/driver-set/vault object (attribute to confirm in a spike; the live reader already reads the per-object `DirXML-pkg*` attributes); and, on upgrade, the three-way merge between old package, new package and customized content. Two facts from this analysis narrow plan.md's open questions: the content checksum class is `com.novell.idm.packages.PackageCRC32 extends java.util.zip.CRC32` with `update(String)`/`update(byte[])` over a `StringBuffer` (i.e., CRC32 of a canonical string, not an opaque hash — decompiling its 30 lines will settle the algorithm), and `PackageChecksum` distinguishes `TYPE_CONTENT` from `TYPE_DIRECTIVE`. Designer's *uninstall+install* implementation of upgrade also tells us Designer itself does not do a semantic three-way merge at the package level; customization survival is handled per item (revert/sync/compare commands), which is the same "baseline + customized flag" model DirXMLDev already keeps in `.package-baseline/`.

Size: large (weeks), and Designer compatibility is the acceptance test (a driver installed by us must be recognized as packaged when Designer imports it from the vault). Recommendation: do Route A first — it delivers install/upgrade now and produces real Designer-made packaged drivers whose vault attributes we can read back to learn exactly what Route B must write.

## 4. Environment-specific configuration

**PDT** has exactly one mechanism: every driver recipe lives *per stage* (`<stageSet>/<stage>/<idv>/<driverSet>/<driver>.json`), and its only environment-specific content is the **prompt answers** — the `driverInputPrompts[{name,type,prompt,value}]` of the base package and of every feature/dependent/mandatory/common package. Those are Designer package prompts, i.e. the GCVs and settings the package's install directive asks for (`XMLParsingImpl` extracts them from resources of content type `application/vnd.novell.dirxml.pkg-prompt+xml`). "Manage environment-specific configuration separately from the reusable package content" therefore means: the package jars are shared (one Designer catalog), the answers are per stage, and *Compare/Migrate* copies answers between stages. Values of type password are stored AES-enciphered (the UI calls `POST /data/encrypt`) and decrypted into the properties file at deploy time. Nothing else varies per stage — no per-stage policy overrides, no per-stage driver settings outside prompts, and after a deploy PDT refuses further configuration changes (docs p. 18, 21, 28: "does not allow you to change configuration values after deploying"). **[code, docs]**

**DirXMLDev** keeps the whole configuration in one tree, vault connection and tier per environment in `environments.properties`, secrets per environment outside the tree, and GCV values in the tree via `gcv.set`. What PDT's model suggests borrowing:

- **Package prompt answers as first-class, per-environment data.** When a driver is installed from a package (Route A or B), record the prompt set (name, type, prompt text, package) in the tree and keep the *answers* in `environments/<env>/prompts/<driver>.properties`-style files; `password-ref`/password prompts resolve through the existing secrets mechanism. The Designer headless `-g` output is the schema source, and Designer's own `.properties` format is worth using verbatim so a file can be handed to `-F` without transformation.
- **A GCV overlay per environment** generalizes that beyond packages: `gcv.set --env stg` writes an overlay the deployer applies when it renders `DirXML-ConfigValues` for that environment (today a value that differs between STG and PRD needs either a branch or a manual edit before each deploy).

Do not borrow: freezing configuration after deployment, prompt-value-only diffs, or storing enciphered secrets in the repo.

## 5. Recommendations

Ranked; sizes are rough engineering estimates.

1. **`idm package.*` catalog reader** — `package.list [--dir <Designer plugins>|--site <url>]`, `package.show SHORT[_ver]` (id, type, base?, features mandatory/optional, dependencies, supported drivers, prompts), `package.resolve --base SHORT_ver [--feature …]` (the dependency closure, mandatory vs optional, using the same `features/optional|mandatory` and `dependencies` elements PDT reads), `package.diff a.jar b.jar` (object/attribute level, our canonical XML). Pure Java over `package_import.xml` + `MANIFEST.MF`; 3–5 days. Evidence: `XMLParsingImpl.getJarEntries`, `PackageDownloadService.readSiteXMLData/readNUpdateFeatureJar/CacheDriverPackages`, `RecipeService.listPackages`, `InstallService.getPackagesToInstall`. Optional: `package.fetch` from an update-site channel (`site.xml` → `plugins/<short>_<ver>.jar`).
2. **Designer-headless runner** — a `DesignerHeadless` class that builds the command line (`-application com.novell.idm.rcp.DesignerHeadless -data <scratch workspace> -command …`), writes the prompt-answers properties file from the tree + environment, runs the process, parses the log for `#OPERATION_SUCCESS`/`#OPERATION_FAILED` and `StatusResult` lines, and never puts a secret on the command line (`-w env:VAR`). Configuration: `designer.home` in `environments.properties` or `IDM_DESIGNER_HOME`. First spike: launch `-command listContents -L P -p <plugins>` on this Mac. 3–5 days plus the spike.
3. **`driver.add --base SHORT[_ver] [--feature …] [--answers file]`** = runner mode 1 (`deployDriver -f`) → `driver.add --from-export`, so a packaged driver enters the tree fully formed and goes through validate/simulate/diff/deploy like any other. Records the installed packages and prompt set in the driver's manifest (the "recipe" idea, in our shape). 1 week after 1 and 2.
4. **`package.upgrade|downgrade|uninstall --driver D --env dev|stg`** = runner mode 2, wrapped: require `vault.diff` empty, snapshot, run, `import-live` into a commit, show the resulting `ModelDiff`, refuse on `prd`. Evidence: `UpgradeService`, `UninstallService`, `InstallService`, `DriverRedeployPackage` (`::` uninstall list), `PackageOperation.installPackageOnTargets`. 1 week. Mark clearly as interim until 6.
5. **Per-environment prompt/GCV overlays** (§4): `environments/<env>/gcv-overrides` applied by `Plan`/`VaultMapping` when rendering `DirXML-ConfigValues`; prompt answers per environment for 3 and 4; secrets for password prompts. 3–5 days.
6. **Native package install/upgrade in the tree (Phase 7)** — after 1–4 have produced Designer-installed reference drivers to compare against. Start with the two spikes this analysis makes concrete: decompile `com.novell.idm.packages.PackageCRC32`/`PackageChecksum`/`PackageUtil` (`installPackage`, `uninstallPackage`, `patchAllGCVValues`, `getDependencyBundles`, `removeCustomizations`, `checkPendingUpgrade`) from `idm.jar` into the scratchpad, and read back from the test vault what a headless install wrote (`DirXML-pkg*` on objects and the installed-package record on the driver). Weeks.
7. **Installed-package inventory on import** — `import-live`/`import-project` already carry per-object package meta; add a per-driver summary (`query packages`) so the tree can answer "which packages, which versions" the way PDT's recipe does. 1–2 days.

Things PDT does that DirXMLDev should deliberately **not** copy:

- A REST server + web UI in front of a file store — every operation is a file edit plus a process launch; the CLI does that directly and keeps the confirmations, gating and `--json` we already have.
- The "recipe" as the model: package ids and prompt answers are not a driver configuration; they cannot be validated, simulated or diffed at the policy level, and PDT's compare is a compare of answers, not of what runs.
- Deploying through Designer's whole-vault `IdentityVault.deploy` with only an exit code as the result — no diff, no plan, no snapshot, no verification, drivers created stopped by side effect of `-v`, security equivalences added silently. Keep our deployer as the only path that writes production.
- Secrets on the command line (`-w <password>`) and enciphered secrets in git keyed to one machine's keystore; Designer itself offers `-w env:VAR`.
- Fire-and-forget operations whose only status is a log file to poll; a hard 5-driver cap; `deleteOnExit` cleanup of plaintext prompt files.
- Using `-m` (mandatory-only) for dependency resolution and hoping the UI catches the rest — resolve explicitly from the catalog.
- Infinispan caches, Kafka/AWS/Postgres config stubs, the hard-coded `environment.json` test fixture (`10.71.131.155`, `admin/test`, `admin/welcome`) and the `D:\Hackfest\workspace\demo\…\DriverTypes.json` path in `api.DriverTypes` — signs of a hackathon-grade codebase; nothing to learn there except caution.
